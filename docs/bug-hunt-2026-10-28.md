# Bug hunt, October 28, 2026

[Architecture](architecture.md) · [3.0 plan](rubylight-3.0-plan.md) · [Stability audit](stability-audit-2026-10-18.md)

This is the write-up of step 4 of the 3.0 work: a read-only review of the
host, Nightjar and the installer for real bugs, plus fuzzing of every parser
that takes bytes from the network. It starts from main `66157f7ac`. The fixes
landed in batch 14 (`a68bc0950..b438174f9`).

## Result

- 49 findings in the reports. Two repeat an earlier one, so 47 are distinct.
- No High. 13 Medium and 34 Low.
- 46 are fixed on main. Five of those keep a limit we accepted (below). One is open.
- Nothing waits on an unmerged branch.
- The fuzzing (the rl-fuzz lane) found one product bug, in the native API percent decoder.

## What was hunted

Reviewers read the code and did not build or run it. Each took one area:

- capture, displays, power and display recovery
- encoders, HDR and Dolby Vision, PyroWave, rate change
- network, input injection and gamepads
- USB forwarding, file transfer, the image clipboard, shared folders
- pairing, permissions, the native API, the console, WebRTC, webhooks, child sessions
- the installer, updater and uninstaller, and the Android app
- audio capture, routing and the microphone, on the host and on the clients
- the Nightjar desktop client and the shared client protocol

Seven areas went first. Follow-up passes covered what the earlier reviewers
did not reach, up to four passes for one area. 26 reports came out of it.

A finding had to name:

- the file and line;
- a failing scenario, with inputs and state, and the wrong result;
- the code path that makes it real;
- a one-line fix;
- its confidence: confirmed (traced end to end) or plausible.

Style notes, "could be cleaner" and guesses without a path were out. The
security areas were also checked for authn and authz on every endpoint and
message, path traversal, size limits, TOCTOU, replay and secrets in logs.

Each reviewer worked within a fixed budget. Several ran out of context and
said what they had not read. Those parts are listed at the end.

### Found while integrating

These came up in the integrator's reviews and the fuzzing, not in a report:

- `4471f848b`: only the newest clipboard sync copy of a device waits. Before, a fast device queued every copy in memory.
- `70b08c36f`: the native API decoded `%+A` in a `?name=` or `?path=` query as a newline. The decoder now takes exactly two hex digits. A property test against a reference decoder found it.
- `306d0a160`: PyroWave frames lost on the network counted as a broken decoder and ended the stream after a loss burst over a second.

- `f24cc8d76`: an upload kept in the view model no longer holds an old screen.

## Accepted risks

Five limits stay. Each one is a trade-off, not an oversight.

- **Per-address connection cap (API-CONSOLE-6).** Each listener serves 512 connections and 64 per address. A peer with many addresses on the LAN can still fill the 512. Those ports serve the local network, and what such a peer costs the host is sockets and tasks, not data.
- **OTP 32 per PIN (API-CONSOLE-3).** Five wrong answers refuse one address. 32 wrong answers across all addresses spend the PIN. The PIN has four digits, so 32 guesses are 0.32 % of the space. Spending a PIN is a nuisance (the user starts pairing again), not a way in.
- **Image upload without a deadline (API-CONSOLE-6).** A request body that stalls for 60 s fails. A body that keeps sending has no total time limit, and neither does a response. A deadline would fail large uploads on slow links. The size is capped by `clipboard_image_max_mb`, only a paired device with the clipboard permission can send one, and a device with an image request waiting gets 429 for the next.
- **A removed PC and a poll in flight (SETUP-ANDROID-8).** A poll now saves and reports a PC only while it is still listed, checked under a lock, and removal marks the PC first. A narrow window against the removal is left. A removed PC can show up again for a moment, and the next refresh drops it.
- **A share sent again after process death (SETUP-ANDROID-6).** A configuration change keeps the transfers and takes a share once. If Android ends the whole process during a transfer, the screen starts again from the share's intent and sends it again. That needs a process kill in the middle of a transfer.

AUDIO-3 is the sixth. The install still holds the audio-route lock while it
waits for the device. Releasing it would let a stream record the auto-selected
Steam endpoint as its original default, or restore over another stream's
routing. The 2-minute backoff limits the hold to one install per 2 minutes.

## Open

- **API-CONSOLE-4: not a bug.** A live session caches neither Host control nor Sleep PC: Close game, the couch menu, Sleep PC and the SleepAllowed offer read the paired state on every request, and Sleep PC checks again right before the suspend. A regression test now proves it (`host_control_and_sleep_turned_off_in_the_console_stop_working_for_a_live_session`): after either permission is turned off, the next request gets 403 and the stream keeps running.
- **Two tests that fail under load.** `the_pairing_qr_code_is_off_until_turned_on` and the WebRTC gamepad listener test failed in some runs under load. We have not found the cause.

## Fuzz coverage

The fuzzing is property tests (`proptest`, 256 cases each, `PROPTEST_CASES`
raises it) and a few end-path tests on the host. It runs in the normal test
gate. It found one product bug (`%+A`) and one overflow in its own fake USB/IP
device.

What is covered:

- **Protocol decoders** (`client/protocol/core/src/fuzz.rs`): every decoder in `rubylight-protocol`. Mutated seeds and arbitrary bytes never panic, and what decodes encodes back to the same value. This includes cursor shapes, FEC reports, keyboard layouts, pen, rate change, roaming, Steam controller, text input, audio chunks, USB forwarding and USB/IP framing, and the text parsers (audio layout, FEC choice, pairing URI).
- **What Nightjar reads from a host** (`client/protocol/client/src`): NvHTTP replies, the XML reader, RTSP responses and DESCRIBE answers, the control session and its wire, and the USB/IP server a forwarded device runs.
- **What the host reads from a client** (`rust/core/src/fuzz.rs`): RTSP framing, requests and the ANNOUNCE SDP, control packet encryption in both versions and its replay window, the legacy input cipher, input packets applied to a USB DualSense, microphone datagrams, FEC status, controller audio and the session journal.
- **HDR and Dolby Vision writers** (`rust/core/src/fuzz/hdr.rs`): HDR10+ and Vivid through independent parsers, SEI and OBU splicing, static metadata, and every Dolby Vision RPU (CRC, final byte, emulation prevention).
- **USB/IP server** (`rust/core/src/fuzz/usbip.rs`): junk, isochronous and out-of-range frames leave the export serving the next import.
- **Host query fields**: launch fields (`rikeyid`, `rlControllers`, the Radeon profile rate) and the native API percent decoder.
- **Control messages in a live stream** (`control_fuzz_tests.rs`): 800 messages of arbitrary kinds and payloads, in the clear and encrypted, leave the stream running and ending normally.
- **Session end paths** (`session_end_tests.rs`): stop and quit, a network drop past the ping timeout, an encoder failure, a host stop, a kick, a replacement and an expired launch each leave `/serverinfo` at zero sessions and zero pending launches, with the display lease, audio route and input slots released.

What it leaves out:

- **Input.** The control fuzz keeps input, keyboard layout, USB, displays, clipboard and server commands out of the live stream, because they act on this PC. The decoders of these messages are fuzzed. The code that applies them is not: the injector stages (`input.rs`, keyboard and mouse, touch and pen) and the Switch Pro and Steam Deck report internals.
- **Displays.** Topology, display recovery and the virtual display lifecycle have review but no property tests.
- **USB.** The wire and the server are fuzzed. Attach and detach on the host, the driver, and the Android USB service are not.
- **Clipboard.** Decoding of PNG and DIB is reviewed. No property test sends arbitrary clipboard data through the host or the clients.
- Packetization, FEC internals and the video send path.
