# Slow-pace latches (#59)
- **No more slow pacing from a decoder that asks twice.** Moonlight, Artemis and Nightjar report every frame they lose, so a second keyframe request from them is their decoder asking again, not network loss. It no longer slows the stream for the rest of the session or for the next day. Measured with a receiver that asks twice for each keyframe, 4K100 AV1 and 1440p120 HEVC: the stream stayed at the fast pace in every run, where the build before slowed down about 3 s in. Clients that don't report their own losses keep the old rule.
- **A stalled network adapter on the host no longer slows the stream for good.** When only the host saw the loss (its own network adapter refused packets, as when a game starts), the slower pace lifts after 10 clean seconds and is never remembered. Measured with a 30 ms send outage at 20 and 40 s: the pace came back at 30 s, and the second outage held it for the session, as before. The pacing history 3.0.0-rc.4 saved, which also held these two cases, is dropped once after the update.
- The host log now names each recovery keyframe's size against its frame cap target, whether it was encoded again from a scene cut, and whether it left without full error correction, and the 5 s `stream timings` lines count keyframes past the cap and past full error correction.
- Experimental: when AMF encodes keyframes more than a tenth over the automatic frame cap, the host lowers the cap it writes for keyframes until they fit, never below two frames' worth, and raises it again once they keep to it. On the RX 7900 XT keyframes kept to the cap, so this changed nothing there (the scale stayed at exactly 1 in every 5 s window).
