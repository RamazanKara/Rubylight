# Video and latency

[Documentation](index.md) · [Settings reference](settings.md)

This page explains the settings that trade picture quality against latency, and the measurements that show the effect of each. For troubleshooting, start from 720p at 60 fps, watch the [performance overlay](#performance-overlay), and change one setting at a time. Resolution determines detail and decode work, frame rate determines motion smoothness and work per second, and bitrate determines compression quality and network load.

## Codecs

| Choice | Use and requirements |
| --- | --- |
| Automatic | Negotiates a hardware codec. Low-latency hardware AV1 is preferred where available, then HEVC and H.264; host capabilities, HDR and decoder checks decide the final choice. |
| H.264 | The most compatible choice, and a baseline when another decoder stalls. |
| HEVC | High quality at lower bitrates, and Main10 for HDR. |
| AV1 | Needs hardware decoding on the device and AV1 encoding on the PC. Compare the decode time on your device. |
| PyroWave | A wavelet codec decoded on the GPU, for the lowest decode time at high bitrates, with hosts that offer it, such as Rubylight. Choose it explicitly; it needs a 64-bit Android device with Vulkan. |

PyroWave requires Android 10 or newer, Vulkan 1.1, and the GPU features, limits and presentation formats the renderer checks for. Start with about 280 Mbps for 720p/60 or 400 Mbps for 1080p/60 on a fast LAN. Tune from there with the overlay. Nightjar requests up to 2000 Mbps at startup and during a stream; the host applies its own ceiling. Nightjar switches to a conventional codec automatically when a device needs it.

With a host that sends PyroWave in records (Rubylight) and the new streaming engine, Nightjar hands each frame's packets to the GPU decoder while the frame is still arriving, so the decoder already holds most of the frame when its last packet comes and only the final records and the decode are left. A frame whose packets came out of order or incomplete is pushed whole as before, which the overlay counts. The picture on screen is always the whole frame. Measured on a Retroid Pocket 6 (1080p60, 400 Mbps, Lowest latency pacing, 50 s per arm in the order off, on, on, off): the median from the frame's last packet to its completed decode went from 3.5 and 3.8 ms to 3.0 ms (p95 from 6.0 to 3.4 ms), and the native submit per frame from 1.8 to 0.8 ms. The median picture age went from 29.2 and 30.2 ms to 28.2 and 28.8 ms (p95 from 33.6 and 35.8 ms to 33.0 and 33.2 ms). Every frame arrived early, and no frame was pushed whole.

A PyroWave host sends each frame as one burst at its link speed. Some receive paths, such as USB Ethernet docks, lose the end of such bursts below the link's rated speed. With a host that supports frame-shaped UDP tests (Vibeshine), **PyroWave frame pace** (under **Settings → Advanced**, or in a PC's own settings, on Android and the desktop) finds the fastest burst speed this device takes without losing frame tails. It saves that speed for the PC and sends it with each PyroWave stream as the host's frame pace. Stop any stream on the PC first; the test takes one to three minutes. The pace belongs to the connection it was measured on, so it is only sent while this device's wired link speed toward the host is the same as during the test.

Run the speed test before increasing bandwidth: **Settings → Streaming → Connection test** (with several PCs, Android asks which one and the desktop has a list beside **Test speed**), or the same test in the PC's own settings. On hosts that support it (Rubylight, or Vibepollo with PyroWave available), its optional, cancellable 32 MiB HTTPS download starts only when requested and reports throughput and the host link speed; see [connection test](TROUBLESHOOTING.md#connection-test).

On Windows and Linux, a PyroWave decoder slower than the stream's frame rate skips to the newest frame instead of queueing frames behind it; skipped frames count as **Decoder drops** in the overlay. On a Radeon 780M laptop with a stream its decoder could not keep up with (7168x4032 at 120 fps), the median delay from the PC's frame to the present fell from 88 to 90 ms to 34 ms. See [PyroWave GPU decoding](pyrowave-decode.md).

### Hardware decoding on Windows and Linux

Nightjar for Windows decodes with D3D11VA on the GPU that draws the window, and Nightjar for macOS with VideoToolbox. Nightjar for Linux tries VA-API first, then Vulkan video, then the V4L2 decoders of ARM boards and handhelds, then NVDEC. Vulkan video is for GPUs without a VA-API driver, such as NVIDIA's: it decodes on the GPU that draws the window, and the picture stays on that GPU until it is shown. It needs the driver's Vulkan video support for the stream's codec and format. On NVIDIA with nvidia-vaapi-driver installed, Nightjar leaves out that VA-API wrapper and decodes with Vulkan video, then NVDEC (`NIGHTJAR_FORCE_VAAPI=1` keeps the wrapper); **Vulkan video first** under **Settings → Debug** puts Vulkan video ahead of VA-API on the GPU renderer. On the GPU renderer, VA-API, Vulkan video and NVDEC pictures stay on the GPU where the driver allows it, and the log says why when they cannot.

Before a stream starts, Nightjar checks what the hardware decoder can decode and offers the PC only that: a codec the device cannot decode streams the next best one it does, and Nightjar says which. If the hardware decoder gives up mid-stream, Nightjar says so, names it on the overlay and moves to the next decoder. When hardware decoding on Linux is missing a piece (a VA driver without H.264 and HEVC, a Flatpak without the NVIDIA driver extension, an NVIDIA driver without Vulkan video), the stream's start says what to install. The overlay names the decoder in use, and a stream that ends up decoding in software says so. With **Video decoding** under **Settings → Debug** on Software, for all PCs or in one PC's own settings, those streams decode in software.

## HDR and color

HDR10 needs an HDR10 display, Android 7+ and a compatible HEVC Main10 or AV1 10-bit decoder, plus HDR configured on the streamed host display. PyroWave has its own HDR-capability checks. Enable **Settings → Video → HDR**, or HDR in a PC's or game's own settings.

Nightjar handles BT.2020/PQ and static mastering metadata. Debug stats show the negotiated format, so you can confirm HDR is active.

### HDR formats

A [Rubylight](https://github.com/RamazanKara/Rubylight) 3.0 PC lists the HDR formats it can send, and Nightjar picks the best one this device's screen and decoder show. Other hosts send HDR10. The overlay names the format in use, and a format that fell back says why.

| Format | What it needs here | Notes |
| --- | --- | --- |
| HDR10 | An HDR10 screen and a Main10 HEVC or 10-bit AV1 decoder | Any host with HDR. The PC's HDR metadata reaches the running decoder instead of restarting it (Android 10 and later); a decoder whose output still lacks it 60 frames later restarts with it. |
| HDR10+ | A screen with HDR10+, HEVC or AV1 | The host's scene statistics travel in the stream. With **Render through Vulkan**, Nightjar passes them on where Android has the call for it; elsewhere the stream stays HDR10 and a message says so. |
| HLG | A screen that shows HDR only as HLG | Also with **Render through Vulkan** and on PyroWave, after Nightjar has asked the screen whether it takes HLG; a screen that refuses gets HDR10, and the status line says so. With an older Rubylight 3.0 PC, PyroWave stays HDR10. Never on packed full chroma. |
| Dolby Vision | A Dolby Vision screen and the device's own Dolby Vision decoder | Profile 10.1 over AV1 where the device has a Dolby Vision AV1 decoder (such as TCL's MediaTek TVs) and the PC offers it, otherwise 8.1 or 8.4 over HEVC. With the automatic codec and a PC that offers only profile 8, the stream uses HEVC. If the decoder fails, the same stream goes on as HDR10 or HLG and the overlay says so. Needs **Render through Vulkan** off and a codec other than PyroWave; Nightjar says so once per PC otherwise. |

On MediaTek TVs, frames reach the decoder without the trailing padding and the HDR Vivid metadata those decoders reject, so Dolby Vision shows as Dolby Vision and HDR10+ as HDR10+.

**Render through Vulkan** shows HDR10 on Android 10 to 14 too, and HLG where the screen's window takes it. If the screen refuses HDR from it, the overlay says the picture is shown as SDR. On MediaTek TVs it runs their decoders without the vendor low-latency settings, which froze it after the first frames; direct output keeps them. When it can't keep up on a display (under 80% of the received frames, or of the display's refreshes when the stream runs faster, for 5 seconds), a message says so once per PC and suggests turning it off.

Nightjar for Windows shows HDR10 and Dolby Vision profiles 8.1 and 10.1, drawn on their HDR10 base layer with the tone-map peak from the Dolby Vision metadata, and draws an HLG stream as HLG. Turn HDR on in the operating system's display settings first.

On Linux, an HDR stream on a compositor that offers HDR10 presents as HDR10 (PQ, BT.2020) and passes the PC's mastering metadata on; where that output cannot be made, Nightjar uses scRGB for the rest of the run and says so in the log. On Wayland, Nightjar describes the picture at the display's own reference white and peak, so the compositor need not convert or tone map each frame and can show it straight on the display; on KDE Plasma 6.5 and later the stream is drawn in the desktop's own HDR format. **HDR brightness follows the desktop** (**Settings → Video**, off by default) makes HDR streams brighter or dimmer with the desktop's brightness instead of showing them at the brightness the PC sends. HLG pictures are drawn as HLG. Under gamescope, see [Steam Deck](steam-deck.md#hdr).

**Less color banding** is for screens without HDR, or with HDR off, where gradients show banding. It streams SDR in 10-bit HEVC or AV1 and needs a Main10 decoder on this device. The PC must offer 10-bit; if it does not, the stream is 8-bit and a message says so once per PC. The PC's display has to be in SDR, because a PC whose display is in HDR sends HDR whatever you chose here, and the status line says so. It is not used with PyroWave, and when HDR is on, HDR wins. The overlay's stream line reads "10-bit SDR" while it is active.

**Sharper colored text** (**Settings → Video**, off by default) keeps colored text and thin lines crisp. On **Automatic**, Nightjar streams full color detail (4:4:4): the codec's own 4:4:4 where this device decodes it and the PC encodes it, else full chroma packed into HEVC or AV1 where both offer it, else 4:2:0, and the app says once per PC why. HDR takes priority over it.

Nightjar for Windows and Linux has both under **Settings → Video**, with the same names and choices. When a stream starts it decodes a short test picture in each codec and offers the PC only what this device's decoder returns as 4:4:4 or 10-bit pictures; a decoder that can't gets 4:2:0 or 8-bit, and the stream names the reason. On Windows, GPUs whose decoder supports HEVC 4:4:4 decode it in hardware, in 8-bit and 10-bit; with **Sharper colored text** on **Automatic** and **Less color banding** on, Nightjar asks for HEVC 4:4:4 in 10-bit where the PC and this computer support it. When HDR takes priority over YUV 4:4:4, the notice says so.

Where the hardware decoder has no native 4:4:4, **Automatic** uses packed full chroma, which keeps the hardware decoder: the PC packs 4:4:4 color into an ordinary HEVC or AV1 stream and Nightjar unpacks it on the GPU. It needs the host option (and on Android the **New streaming engine**); the row is hidden with PyroWave, which has its own chroma modes. Before a stream starts, Nightjar checks the PC's modes and this device's decoders: a stream that can't have full chroma starts without it and says why, and when the PC refuses it after the game has started, the stream starts again at once without it and resumes the game. A PC that refused it is asked again after Nightjar or the PC is updated.

**Full color range** (**Settings → Debug** on Android and the desktop) is an explicit override: mismatched range can crush blacks or clip highlights.

## Refresh rate and VRR

With VRR off, **Frame pacing** balances immediate response against regular presentation. **Lowest latency** favors fresh output; **Balanced** aligns cadence to the display's vsync when the stream is slower than the panel (60 fps on 120 Hz), and, from a host that takes phase-lock reports, releases frames as they come out when the stream is about as fast as the panel or faster, where waiting for the vsync callback dropped one frame in sixteen at 120 fps on a 120 Hz panel (other hosts, and **Drop late frames** off, keep the vsync queue); **Balanced with FPS limit** and **Smoothest video** retain more queued output.

For conventional codecs, the two smooth modes preserve normal output order within one stream-frame interval. When an output is older and a newer decoded frame is already available, they discard the older decoded output to recover from backlog. A last frame with no replacement is still shown. Catch-up is bounded by one frame interval of work and a buffer-count limit; compressed reference frames are kept. A decoder can also hold a newer frame back inside it, so no newer output is ever ready to swap in. The display's own queue can also hold one buffer too many, so the decoder waits for a free buffer and input-to-output time rises with nothing behind the held output (10 to 12 ms for 45 seconds on an NVIDIA Shield). When input-to-output time stays at least half a frame above its lowest value since the last flush for 80% of the outputs in 1.5 seconds, the smooth modes wait up to 2 ms for a newer frame that is in the decoder behind the held output, and drop the held output only if that frame comes out; with nothing behind it, they drop the held output at once and the screen keeps the previous frame for one refresh. They drop one at a time, re-measure after each drop, and stop once the excess is gone. A drop that changes nothing, or 60 waits without a newer output, mean the delay is the decoder's own (deeper pipelining in motion, or frames it discarded after loss): the floor rises to that level and the smooth modes pause until 1.5 seconds look healthy, so the next scene change does not start it again. Eight drops pause it without moving the floor. The frame-timing CSV marks these drops `debt` in `drop_reason` and fills `queue_depth` and `residency_excess_ms`. Drift between the display's and the host's clocks costs one drop each time it adds up to half a frame; healthy recorded streams never reach the threshold.

On a Shield's decoder (`omx.nvidia.*`, `c2.nvidia.*`, the only one these captures came from), the wait for a display buffer is caught much earlier than half a frame; every other decoder keeps the half-frame rule, and a floor raised at any level. A stream a little faster than the panel fills the display's queue slowly (45-50 ppm, about 0.05 ms a second, on the Shield captures), and a frame the compositor misses adds a whole frame that nothing takes back, since these modes show every frame. Once the queue is full, the drift goes into input-to-output time, which took two to two and a half minutes to reach half a frame. An output that leaves as soon as it is decoded follows its input's timing; one waiting for a buffer follows the display's. So on that decoder the smooth modes also take the slope of output intervals over input intervals across 10 seconds, from the time just before the queue call: with the slope under 0.3 by two standard errors, the time at least 1 ms above its recent level (the lowest tenth of the last minute's seconds, each by its lowest fifth) for 80% of the outputs and of the last second's, and frames behind at most 10% of them, they drop the held output with nothing behind it. The drift needs one such drop for each frame it adds; the replays hold one drop each, so they do not show how often that comes. Replayed with a frame of room per drop, which the replay assumes and cannot show, input-to-output above 2 ms lasted 12 to 18 seconds instead of 130, with the drop at about 3.4 ms instead of 8.7, and steady parts dropped nothing. A start that is at its level from the first seconds has no recent level below it, and keeps the half-frame rule.

If outputs still follow the display 5 seconds after the drop, or a drop with nothing behind it leaves over half a frame, they were not waiting for a buffer, and this check stays off until the next flush. A drop that left more than half of the wait in place changed nothing, and the next one waits 10 minutes, twice that after another. 24 drops since a flush turn it off too. Inputs with under 0.1 ms of spread give it nothing to measure. On that decoder a level over three frames does not raise the floor the first time, since a start-up burst reaches 70 ms and more and a floor that high would hide every later rise; the same level again is the decoder's.

For PyroWave, paced modes map the host's frame timestamps onto the display clock instead of presenting every arrival immediately. Balanced keeps a small scheduling margin; Balanced with FPS limit and Smoothest video add one refresh of buffering. The queue stays bounded, so an overloaded decoder or a network stall cannot build an ever-growing delay. Missing host timestamps use immediate presentation, and a pause or timestamp discontinuity restarts the mapping. Lowest latency and VRR keep immediate presentation.

**Take back display queue delay** (**Settings → Display & image**, beside Frame pacing, on by default) covers **Lowest latency** and **Balanced** on a fixed refresh, where the device reports when frames are shown. When the display keeps frames waiting a whole refresh longer than the stream's own level for 3 seconds, Nightjar drops one frame so the display gives that refresh of delay back, then checks the wait again; drops that change nothing turn it off for the stream. The log shows each step as a `Display queue:` line. With **Show frames at the PC's frame times** on, frames are scheduled instead and the setting is hidden. The desktop clients have no compositor queue of this kind and no such setting.

**Show frames at the PC's frame times** (off by default) schedules each frame on a fixed-refresh panel from the host's frame timestamps: the frame goes to the vsync nearest to its time on the PC, never earlier than the first vsync it can make, and is never held longer than releasing it at once would hold it. A frame that would share its predecessor's vsync moves one vsync later, and never more than one vsync past the first it could make. Two frames in a row move only when the stream is no faster than the panel and the second frame is due at most an eighth of a refresh before that vsync: capture jitter then puts two frames' times on either side of a vsync boundary, which a slow drift between the PC's clock and the panel's keeps doing for seconds at a time. The panel's refresh interval does not otherwise delay frames, so a 60 fps stream on a panel that reports a rate a little below 60 Hz keeps its usual hold. The schedule tolerates the lateness of three quarters of recent frames; a later frame still takes the first vsync it can make.

Measured on a Retroid Pocket 6 (120 Hz panel), median time from receipt to SurfaceFlinger's present time, two 60-second runs per arm:

| Stream | Off | On | Display jitter p99, off / on |
| --- | --- | --- | --- |
| 90 fps | 17.22 ms | 17.97 ms | 11.2 / 9.2 ms |
| 60 fps | 20.03 ms | 17.97 ms | 8.7 / 8.6 ms |

Present times come from `dumpsys SurfaceFlinger --latency`, not from the moment the client hands a frame over: a frame released at once waits in SurfaceFlinger's queue, while a frame released with a due time does not, so hand-over times would make the scheduler appear about 15 ms later than it is. Absolute values varied between sessions, so compare arms within one session.

The Vulkan renderer uses measured refresh timing and actual presentation feedback when the driver supplies them. On the local display, Android's frame callbacks provide a measured clock as a fallback. Supported drivers also report how early a frame could have appeared and its timing margin; Nightjar uses these to learn the submission lead time, with bounded adjustments and a settling period after pauses. These changes target display cadence and missed refreshes; they do not reduce the shader's execution time.

For H.264, HEVC and AV1 on the local display, Android 13 and newer supply each vsync with its own timeline: when a frame queued now will be shown, and by when it must be queued. Nightjar takes the vsync times and that deadline from it instead of the display's fixed vsync offset and presentation deadline, which are configured values rather than the timeline SurfaceFlinger actually runs; values that cannot be right keep the fixed ones. The scheduler for **Show frames at the PC's frame times** and the phase-lock reports both use them. The log notes the deadline (`Vsync timeline: buffers due … before their vsync`) next to the display's reported one whenever it changes by a millisecond or more.

With **Variable refresh rate** on, Nightjar requests a stream at the screen's maximum refresh rate and presents decoded frames immediately. Compatible hosts are also asked for their VRR streaming policy. When Android 16 or newer reports ARR support, Nightjar clears its fixed refresh requests and lets Android infer the display cadence from presented frames. Other screens use a maximum-refresh fallback. VRR forces Lowest latency pacing and disables Allow lower refresh rate.

The Debug overlay's **ARR** or **max Hz** label identifies the refresh policy selected when the stream started. On Android 16 or newer, **max Hz** means Android did not report ARR support for the output's active mode at that point. The Android version and an adaptive-refresh screen specification alone do not establish support for Android's ARR interface; the device firmware must expose it. Host-side VRR cannot change this capability. See [Android's ARR requirements](https://source.android.com/docs/core/graphics/arr).

**Panel Hz** is the selected display mode's peak rate, not a measurement of instantaneous panel refresh. A steady 120 Hz value therefore cannot establish whether ARR is working. For troubleshooting, **Report a problem** includes `Display refresh` entries with the Android API, output and mode numbers, raw ARR capability, selected policy and refresh requests. These entries track changes during the stream without recording display names or hardware identifiers. Fixed-refresh latch estimates are suppressed while Android reports an ARR-capable mode.

**Match the screen to the game's frame rate** (off by default) makes the frame rate vote follow the game. From the host's frame timestamps Nightjar measures the rate the game presents at (the median interval over one second). After it has held within 3% for two seconds, the rate is voted to Android with `Surface.setFrameRate`, seamless changes only, so the screen can move to a mode that divides it evenly (60 Hz for a 60 fps game in a 120 fps stream) without going blank. A new rate must also hold for two seconds, differ by more than 3% from the last vote and arrive at least two seconds after it. It needs a host that announces clock sync (Rubylight) and Android 11 or newer, and is skipped with VRR, a TextureView and PyroWave. With **Allow lower refresh rate** off the vote never goes below the rate that setting keeps, so the game's rate can then only raise it; turn that option on (or choose Balanced with FPS limit or Smoothest video) for the vote to lower the screen. A screen with no matching seamless mode stays where it is, and `Display refresh` entries in Report a problem show each vote.

Per-PC profiles accept rates to 0.01 Hz, such as 59.94 or 119.88. Hosts that support fractional rates (Apollo, Vibepollo and Rubylight) receive them as set; other hosts receive a whole-number rate. The overlay reports received, rendered and on-screen FPS separately from panel refresh.

### Refresh rate on Windows and Linux

**Variable refresh rate** (**Settings → Display & image**, on by default) uses G-Sync, FreeSync or HDMI VRR where the display has it on: each picture is shown as soon as it is ready. Without VRR, **Frame pacing** offers the same four choices as Android and **V-Sync** decides whether a picture waits for the display's refresh (on) or may tear (off). On Windows, a fullscreen VRR stream below about 70 % of the display's rate, or on a monitor that turns out not to refresh on present, waits for the refresh instead of tearing, and the overlay says so; on Linux, Nightjar asks the graphics driver whether the display actually runs VRR, and the overlay reads "V-Sync: this display does not refresh on present" when it waits. **Show frames at the PC's frame times** works with VRR. With V-Sync on, controller input and mouse clicks are sent while a frame is being shown instead of after it; see [mouse pace](mouse-pace.md).

## Video size

**Settings → Display & image → Video size** decides how the stream fills a screen of another shape. The stream menu's **Video size** changes it during a stream when no upscaler or PyroWave is active; with either of those it applies to the next stream.

| Mode | Result |
| --- | --- |
| Fit (default) | The whole picture, with bars on the sides or above and below. |
| Fill (crop) | Fills the screen without distortion; the edges that do not fit are cut off evenly. |
| Stretch | Fills the screen; shapes look wider or taller. |
| 1:1 pixels | One stream pixel per screen pixel, centred. A smaller stream gets a border; a larger one is cropped. |

**Video position** (Centre or Top) places a Fit or 1:1 picture that leaves room: Top keeps the space below free, for the soft keyboard or the lower half of a half-folded phone. Fill and Stretch cover the whole screen, so the position changes nothing there. Fill and Stretch also use the area beside a camera cutout, like a stream at the panel's own size; Fit and 1:1 keep to the cutout-safe area. Picture-in-picture always shows the whole stream (Fit, or Stretch if chosen).

Scaling is a view transform only: the decoder, its buffers and the frame path are unchanged, and touch, mouse, pinch zoom and the Local cursor map through it (see [touch mapping](controls.md#touch-mapping-and-video-scaling)). With an upscaler, Fill draws the cropped edges too, so it costs a little more GPU time than Fit; 1:1 shows the stream at its own size, so there is nothing to upscale.

## Orientation

**Settings → Display & image → Orientation** decides which way the stream screen may turn. **Automatic**, the default, keeps phones in landscape and lets tablets, squarish screens, desktop-class devices, split-screen or desktop windows and external displays turn freely.

| Choice | Screen | Stream shape |
| --- | --- | --- |
| Automatic (default) | Phones in landscape; the others turn freely. | Unchanged. |
| Landscape | Locked to landscape, either way up. | Unchanged. |
| Portrait | Locked to portrait, either way up. | Portrait from the start on a host streaming from its virtual display. |
| Rotate with device | Follows the device, unless the system rotation lock is on. | Starts in the screen's shape on a host streaming from its virtual display, and turns with the device where that host also resizes a running stream. |

Only a host that draws the stream on its own virtual display can give it a portrait shape (Apollo, Rubylight and Vibepollo with the virtual display on; see [host support](PARITY-MATRIX.md)). With **Rotate with device**, Nightjar then asks the host for the turned size during the stream, through the same in-place resize used for foldables. A turn waits one second for the device to settle, so turning the phone over and straight back sends nothing. As for foldables, the decoder is readied for the new size before the host is asked, and nothing waits on the video path. A fixed resolution is turned as it is (1920×1080 becomes 1080×1920); a native one follows the panel. Sizes are rounded down to even numbers and to the decoder's alignment, and shrunk with their shape kept if the decoder cannot take the turned size at full height.

Every other host, and a host that cannot resize a running stream, keeps the stream's size: the picture is placed in the turned screen by [Video size](#video-size), with bars or cropping as chosen, and Nightjar says so once per stream. The same notice appears if the device's decoder cannot switch to the turned size. A stream on an external display ignores the phone's orientation, and the setting is hidden on TVs.

Touch, mouse, pinch zoom, the Local cursor and on-screen controls map through the laid-out picture, so they stay aligned after a turn. The on-screen controls are laid out again for the new screen shape; their layout was designed for landscape and is roomier there.

PyroWave handles display rotation during its existing color-conversion or upscaling pass, including letterboxing. It recreates the output buffers when the surface size or rotation changes, including a half-turn with unchanged dimensions. This can avoid a separate compositor rotation pass; the performance benefit depends on the device.

## Upscaling

Choose **Settings → Display & image → Upscaling** or override it in a PC profile. First lower **Resolution**, for example to 720p on a 1080p screen. A PC profile also accepts a custom stream resolution. This reduces transmitted pixels and decode work; upscaling reconstructs that smaller video at the Android output size. **PC render resolution** changes the PC's render resolution, not the transmitted video size.

| Mode | Processing |
| --- | --- |
| Off (default) | Direct output without FSR/SGSR reconstruction. |
| Smooth | Bilinear scaling through GLES for MediaCodec or Vulkan for PyroWave. |
| Sharp (FSR) | AMD FSR 1.0: EASU reconstruction followed by RCAS sharpening. |
| Sharp, Snapdragon (SGSR) | Qualcomm SGSR 1: single-pass spatial reconstruction. |

MediaCodec GPU upscaling requires lower-resolution SDR video, GLES 3.0 and the required external-image support. Native/larger input, HDR and 10-bit use direct output. Under GPU overload or after a resize, this path switches to direct output for the rest of the session; reconnect to retry.

PyroWave SDR streams use SGSR 1 inside the Vulkan renderer for both FSR and SGSR, reading the decoded planes directly in one pass. The output follows the actual Android surface size independently of the decoded stream size. It preserves the video's aspect ratio unless **Video size** is Stretch. Upscaling needs an output viewport larger than the source; HDR/10-bit and a failed SGSR pipeline keep direct output. The Debug overlay shows the active path or the reason it is inactive.

Sharpening ranges from 0–100%, default 50%. At 0%, FSR bypasses extra sharpening; SGSR still performs spatial reconstruction. The setting applies next stream. Compare text, edges, motion, battery use and added time, not just a still image.

## Frame Warp

**Frame Warp** (Video settings on Android and the desktop, off by default) shows a mouse or right-stick camera turn on the next refresh of this screen instead of a network round trip and the game's own delay later. Each picture is shifted by the part of your turn the PC has not drawn yet, and the game's HUD (crosshair, health, minimap, weapon) stays where it is. On a screen faster than the stream, such as a 60 fps stream on a 120 Hz screen, the picture is drawn again with a new shift between frames while you turn, so the turn moves at the screen's rate.

It needs a PC that offers it (Rubylight). The PC learns each game while you play: how far the picture moves per mouse count and per second of stick, how long the game takes to show an input, and where the HUD is. Until a game's model locks, the overlay reads **Frame Warp: learning** and nothing is shifted; a PC remembers what it learned for the next session. Menus, cutscenes and a mouse pointer unlock it again.

What to expect:

- The shift is a translation. It is right for a camera turn, approximate near the screen's edges at a wide field of view, and it does not predict moving or strafing. While turning, the edge the picture moves away from shows a darkened mirror of the picture until the PC's frame arrives.
- A HUD element that moves or fades can be shifted for a moment, and a scene that hardly changes can keep a few cells unshifted.
- Turning the in-game sensitivity refits within a few seconds. Mouse acceleration in the game makes the fit worse and can keep it from locking.

The Statistics and Debug overlays show its state: not offered by the PC, learning, or locked with the learned gain, the game's delay and the current and largest shift.

On Android it needs the New streaming engine. It draws through Vulkan where the device has it (Android 10 and newer), even if the renderer was not set to Vulkan, or else through OpenGL ES without upscaling; PyroWave streams draw it in PyroWave's own renderer, with its upscaling and HDR. It is off for a stream with Full chroma, and for HDR on a device without Vulkan, with a message saying why. On the desktop every presenter draws it; with beam racing on, the shift is set once per frame and the picture is not drawn again between frames.

The protocol is described in [Frame Warp](protocol/frame-warp.md).

## Snapdragon GPU drivers

**Settings → Advanced → Snapdragon GPU driver** selects the Vulkan driver used by PyroWave; it is shown on arm64 Adreno devices only. **System GPU driver** is the default. Custom drivers require Android 10+, an arm64 app and an Adreno GPU; they do not replace Android's system driver or the MediaCodec drivers used by H.264, HEVC and AV1. The selected driver must still pass PyroWave's Vulkan checks.

Use **Import driver ZIP** to import and select a trusted Adreno package, or choose an already imported driver. Import and selection refresh the capability check; the next stream uses the selection. **Remove a driver** deletes its private app copy and returns to the system selection if that driver was selected. Stop a stream before removing its active driver. Imported drivers are excluded from app backups.

Packages need a root-level `meta.json` with schema version 1, a compatible `minApi`, name, author, package/driver versions, Mesa or Qualcomm vendor, and the named arm64 `.so` library. The importer rejects folders, unsafe or duplicate paths, non-arm64 libraries and oversized packages. Limits are 128 MiB compressed, 256 MiB expanded, 64 files, 16 KiB metadata and eight installed drivers. Package validation does not establish compatibility with a particular GPU.

If loading, capability checks or initialization fail, Nightjar tries the system driver and reports the fallback. A failed custom selection remains available to retry or remove. If the app exits while a custom driver is active, the next launch returns that selection to the system driver. Loaded driver libraries and capability results remain in the process until it exits; switching drivers affects a new stream without unloading libraries from an active one. To retry a failed load of the same installed package, fully close and reopen the app, then select it again. The Debug overlay shows the driver each stream used. Custom drivers are optional and do not guarantee a speed-up; compare performance and stability on your device.

## Sound

Nightjar plays stereo, 5.1 and 7.1 Opus, and 7.1.4 from a Rubylight 3.0 PC on a 12-channel output (Android 12L or newer on Android), with low-latency AAudio for stereo on Android 8.1 and later. A lost or late audio packet is filled in from the sound before it instead of a gap of silence, and the audio that arrives late after a network stall is skipped, so audio latency stays where it was. When this device's audio clock runs a little slower than the PC's, the extra audio is trimmed one packet at a time with a short fade, so latency does not creep up.

**Mute audio** (**Settings → Audio**, off by default, on Android and desktop) streams without sound on this device; the microphone and **Play audio on the PC too** keep working.

**Audio passthrough** (**Settings → Audio**, off by default) is for a receiver, soundbar or TV that decodes Dolby Digital or Dolby Digital Plus, or takes multichannel PCM as is. Nightjar asks a Rubylight PC for a format the audio output reports it plays and keeps Opus otherwise, with a message. On Android it needs Android 10 or later and the New streaming engine. Nightjar for Windows and Linux asks for PCM. Dolby audio comes in frames of 32 ms where Opus uses 5 ms, so a sound reaches the network up to 27 ms later; with the codec delay that is about 30 ms at worst before the client, plus the receiver's own buffering ([measured 2026-10-27](https://github.com/RamazanKara/Rubylight/blob/main/rust/PERFORMANCE.md#october-27-audio-passthrough-encode-cost)). Opus stays the default for that reason.

The microphone and its effects are under [controls](controls.md#microphone).

## Performance overlay

Show or hide the overlay with the stream menu's **Overlay** tile (RB on a controller) or **Ctrl+Alt+Shift+S**, and choose **Compact**, **Statistics** or **Debug** on the **Diagnostics** tile's **Overlay and diagnostics** page. The saved default is under **Settings → Streaming → Performance overlay**, a picker with Off, Compact, Statistics and Debug, all always available. **Copy stats** copies the full Debug text regardless of visible mode. The overlay hides in picture in picture.

Compact is the default: one line such as `● 119.9 FPS · 8 ms RTT · 0.1% loss`, with rendered FPS, the measured network round trip (labelled RTT, not end-to-end latency) and frame loss. The dot is green, turns amber from 1% loss, a 40 ms round trip, a tenth of the received frames not rendered or decoding slower than a frame, and red from 5% loss, an 80 ms round trip or a quarter of the frames not rendered. A stream faster than the screen's refresh rate is judged against that rate instead, since the screen cannot show the extra frames, and the line says so: `● 103.0 FPS · 60 Hz screen · 8 ms RTT`. Compact sits top-start, moves to a free corner or the top centre when on-screen controls would sit under it, and keeps clear of camera cutouts. Statistics shows stream resolution/codec/color with the received FPS, rendered and received FPS, received video payload Mbps, network frame loss, network RTT and variation, host processing, decode time and display wait. These are separate measurements: adding network RTT and decode time does not measure end-to-end latency. Payload Mbps excludes audio, protocol overhead and retransmissions, so it is not the configured bitrate or total link traffic.

Unavailable measurements display **—**, not zero. Some devices or rendering paths cannot report display callbacks, and host processing requires host-provided data. **Measure input latency** runs a separate input-to-rendered-frame probe; neither overlay mode infers that measurement from the displayed stages. Optional [host hardware metrics](#host-hardware-metrics) appear separately from these timings.

Debug groups diagnostics into Video, Network and Decode and scrolls on smaller screens. It adds timing percentiles, decoder settings, GPU driver and upscaling details where available. Existing Advanced selections become Debug. Statistics ends with a status line of lasting facts about the stream, such as HDR or a codec this PC or device lacks; each is also said once per PC as a message.

| Debug metric | Meaning and interpretation |
| --- | --- |
| Resolution, codec, HDR/chroma, decoder | Actual negotiated stream and selected decoder; compare with requested settings. |
| Received / rendered FPS | Frames received and frames submitted for display. Rendered FPS counts every frame released for rendering, whether or not the platform reports a render callback, so it is available on devices without callbacks. Low rendered FPS with healthy receive/decode rates points toward frames dropped before display. |
| Presented FPS | Frames the platform confirmed through render callbacks (on the Vulkan renderer, queued presents). Shown only when the device reports them. Rendered FPS well above presented FPS points toward frames the compositor dropped or delayed; the compact overlay's dot also uses this rate when it is available. |
| Estimated display drops | The share of the frames released in a two-second window ending five seconds ago whose presentation callback never came (after five seconds) or that the renderer replaced. The window lags so that every frame in it is decided and the drops and the frames they are a share of cover the same time. **—** without render callbacks or before such a window. The frame-timing CSV keeps the stream's total. |
| Network latency / variation | Control-channel round-trip time and its variation in milliseconds. |
| Network frame loss | Frames lost through the transport/recovery path, expressed as a percentage; separate from local decoder/display drops. |
| Decoder drops | Frames this device received but dropped because the decoder fell behind. They are not network loss: loss, **Lower bitrate when the network is busy** and the stream health report count only what the network lost. |

The total over the last two seconds is divided by all frames received in that time; the figure after streaming does the same over the whole stream. It excludes pre-input queue wait and later display wait. The median and p95 beside it, and the frame-timing CSV, use exact per-frame times from input submission to decoder output. |
| CPU submission time (PyroWave) | CPU wall time around the native submission call, divided by all received frames, including skipped frames. Fractional milliseconds carry across frames and reporting windows; the displayed average combines the last two one-second windows. The stream-end average includes closed reporting windows only. This measures preparation and submission, not GPU completion or display wait. |

| Display wait | Decoder output to Nightjar's hand-off to the display: on the direct MediaCodec path, the time Nightjar asked Android to show the frame (the release, or the later display time it was released for, such as a frame held for the PC's frame time); on the Vulkan and PyroWave renderers, the queued present. Android's compositor and the panel come after the hand-off and are not part of it, on every path, as in Nightjar for Windows and Linux. That later part, decoded to on screen, is logged every five seconds where the device reports it, and the stream-stutter report judges it. |
| Frame pacing | Average interval between shown frames, jitter, judder, how many vsyncs each frame took, and a timeline of the last frames. With a stream faster than the screen, judder is not measured (every interval sits near half a vsync, where rounding splits them by noise) and the vsync counts and timeline are left out. |
| Client latency | From the complete frame to the same hand-off as Display wait: Queue wait, Decode time and Display wait together, Nightjar's own part of the path. The time the frame's packets take to arrive is network time; the frame-timing CSV has it (`receive_ns` to `enqueue_ns`). |

| Host processing | The video frame header's per-frame processing time, the value Moonlight shows; avg/median/p95 here, and the statistics overlay's line is the average over the last two seconds. ## Host hardware metrics

This needs a host that sends hardware readings (Rubylight 3.0). Turn on **Send hardware metrics to client** in the host's settings (**This PC → Hardware metrics** in Rubylight's console); it is off by default. Start or reconnect a video stream and show the **Statistics** or **Debug** overlay. The client checks the host's advertised protocol support; the host version number alone does not establish compatibility. Normal streams and Remote Monitor qualify, but input-only sessions do not. Pairing and **View streams** or **Launch and quit applications** permission is required, and the active video stream must belong to this device.

Statistics adds host CPU usage and each reported GPU's usage, temperature and GPU power. Debug adds a **Host hardware** section with GPU names/IDs, available clocks, hotspot/memory temperatures, voltage, fans, GPU/board power, VRAM readings and sample details. GPU readings need an AMD driver with ADLX support; Windows CPU usage can be available without an AMD GPU. CPU temperature and CPU clocks are not provided. These are host-wide readings, not per-game measurements; a listed GPU is not necessarily the capture or encoding GPU.

The host's **Hardware metrics selection** controls which readings it sends; an empty selection requests all supported readings. Each reading is optional, and missing values appear as **—** rather than zero. A present zero, such as a stopped fan, is valid. The first CPU sample can be unavailable. Each new sample replaces the previous readings, including any GPUs that are now absent. Failed or stale samples remove the extra hardware section; a valid empty sample shows CPU usage as unavailable. Stream-provided **Host processing** time remains independent of this feature.

Requests use the paired streaming HTTPS connection, independently of video decoding. Android polls at most once every two seconds, or less often when the host's sampling interval is longer. Polling stops when the overlay is hidden, the app is paused or in picture in picture, or the stream ends. Temporary failures clear the values and retry with backoff; denied access, an unavailable endpoint or an unsupported schema stop telemetry for that session. After enabling the host setting or restoring permissions, reconnect to rediscover support. **Copy stats** includes available hardware readings and GPU names. See the host's [hardware metrics protocol](https://github.com/RamazanKara/Rubylight/blob/main/docs/hardware-metrics.md) for field definitions and units.

## Network drops

When the network goes silent for a moment (a phone roaming between Wi-Fi access points, a short dropout, a VPN such as Tailscale moving between Wi-Fi and mobile data), the stream does not end straight away. Sends that find no route are treated as lost packets and resent. What ends the stream is the control connection's timeout: by default, 10 seconds without hearing from the host.

**Settings → Streaming → Wait through network dropouts** raises that timeout to 15, 20, 30 or 60 seconds. It is off by default, because a longer timeout also keeps a stream that is really gone on screen for longer. While the network is silent the picture freezes. Once nothing has come back from the host for a second, Nightjar stops sending input instead of queueing it for later, so a long silence does not end in seconds of old input arriving at once. When the host answers again, Nightjar sends where things stand now: keys and buttons let go meanwhile are released, ones still held are pressed, controllers send their current state, and touches are cancelled. Mouse movement, scrolling and text from the silence are dropped, and input from its first second can still arrive late. The next video frames resume the picture.

The host has its own timeout for a silent client, usually also 10 seconds, and it ends the session on its side when that runs out. A wait longer than 10 seconds therefore only helps if the host is set to wait as long. Sunshine and its forks (Apollo, Vibepollo) call this `ping_timeout` in the host configuration, in milliseconds; NVIDIA GameStream has no such setting.

If the network does not come back in time, the stream ends with an error that says the drop tolerance ran out (or that the host may have ended the session first). With [**Recover interrupted streams**](recovery-and-quality.md#recovering-a-connection) also on, Nightjar then reconnects to the same running game within its usual one-minute budget.

The setting covers the network path staying the same, which is the case for roaming within one Wi-Fi network and for a VPN that keeps its address. A change of the device's address that the host can see, such as leaving Wi-Fi for mobile data without a VPN, needs the host to accept the client from its new address, which Nightjar cannot do alone. The proposed [client roaming](protocol/client-roaming.md) protocol extension addresses this case.

## Lower bitrate when the network is busy

For bounded reconnects and opt-in resolution/FPS adaptation, see [stream recovery and automatic quality](recovery-and-quality.md).

Turn on **Lower bitrate when the network is busy** under **Settings → Video**, directly below **Bitrate**, or under the stream menu's **More**, with a host that reports its stream bitrate (Rubylight 3.0). On a Sunshine-based PC with its own automatic bitrate, turning it on starts the PC's controller instead, which follows the network reports Nightjar sends every three seconds. It is off by default. The Settings switch is the default for every PC and the bitrate setting is the most it uses; the stream menu saves a choice for one PC, separately for conventional codecs and PyroWave. Changing the Settings switch makes every PC follow it again. Loss, RTT variation and completed decode headroom inform adaptation; PyroWave also considers queue delay. After trouble, the bitrate steps back toward the last rate that ran without poor samples in big steps once the link is healthy, and probes above it slowly. Jitter or queueing that does not drop after two cuts is not cut further (loss still is). See [stream recovery and automatic quality](recovery-and-quality.md#lower-bitrate-when-the-network-is-busy). Manual session bitrate changes turn it off.

### Bitrate, frame rate and error correction with a Rubylight PC

- **Change bitrate / frame rate.** With a host that accepts rate changes during a stream (Rubylight 3.0), the stream menu's **Quality** tile opens this one control in place of Set bitrate. The PC's answer, a limit it applied or a refusal shows as a message.
- **Lower bitrate when frames are lost**, under **Settings → Debug** (off by default): this device lowers the bitrate when frames are lost and raises it again after clean seconds, without a keyframe, in place of **Lower bitrate when the network is busy**. It needs the **New streaming engine** and a PC that offers bitrate changes; other streams use **Lower bitrate when the network is busy**. The desktop has the same setting there.
- **Error correction**, under **Settings → Debug** (Android and desktop): **PC's setting** (the default) leaves the share of recovery data to the PC; **Automatic** asks it to follow the losses this device reports; **10 %** to **50 %** fixes the share. Rubylight 3.0 and Sunshine-based PCs that accept the request take it. Both streaming engines report lost video to the PC once a second, which is what Automatic follows. On shaped Wi-Fi-like links on 2026-10-27, Automatic lost less and froze less often than the PC's own adaptive share ([measurement](https://github.com/RamazanKara/Rubylight/blob/main/rust/PERFORMANCE.md#october-27-client-error-correction-and-a-link-test-before-the-first-bitrate-nuc)).
- **Test the link before starting**, under **Settings → Advanced → Diagnostics** (off by default): a new stream at the automatic bitrate first times a short download from the PC (Rubylight 3.0) and starts at no more than 80 % of the result, never below 2 Mbit/s. It is off by default because it started streams lower, with more loss, in our measurement on 2026-10-27 ([client error correction and the link test](https://github.com/RamazanKara/Rubylight/blob/main/rust/PERFORMANCE.md#october-27-client-error-correction-and-a-link-test-before-the-first-bitrate-nuc)).
- **Tell the PC when on Wi-Fi** and **Tell the PC the link speed**, under **Settings → Debug**: a host that uses these hints (Rubylight 3.0) paces the stream for this device's connection from the first frame.

Use **Settings → Advanced → Export latency CSV** to save the latest local frame timings. `queue_wait_ms` and `input_to_output_ms` correspond to Queue wait and Decode time, and `output_to_render_ms` runs to the render time: on screen on the direct path and with PyroWave (Display wait plus Android's compositor and the panel), the queued present with the Vulkan renderer; the appended FPS sample separates received/released/shown FPS and estimated presentation drops.

For direct MediaCodec output, `render_ns` keeps the platform's render timestamp. The appended `callback_received_ns` records arrival at Nightjar's listener, before taking the statistics lock; `callback_delay_ms` is arrival minus the reported render time. These fields do not change Display wait or shown FPS. Android can delay and batch callbacks, and older Android versions can omit some callbacks. Delayed delivery alone does not increase `output_to_render_ms`, but a device's reported render time can still reflect its surface/driver behavior. Compare `decoder_output_ns`, `release_ns`, `render_ns` and callback arrival to distinguish app-held output, post-release delay and notification delay. The CSV alone cannot establish physical presentation latency. See [Android's callback contract](https://developer.android.com/reference/android/media/MediaCodec.OnFrameRenderedListener).

The nine columns after `callback_delay_ms` join a row with the host's own timing record (Rubylight's `docs/timing-record.md`): `rtp_host_us` (the frame's RTP time in host microseconds), `host_present_us`, `host_acquired_us`, `host_submitted_us`, `host_encoded_us`, `host_first_sent_us` and `host_last_sent_us` (from an extended 0x5536 host timing report, on the host's video clock), then `clock_offset_us` and `clock_rtt_us` (the clock sync offset, `client = host + offset` against `System.nanoTime()`, and the round trip of the exchange it comes from; the offset is read once per CSV flush). A column is empty where its source is missing: the host stamps for a host that sends only v1 reports, the offset for a host that does not announce clock sync. Clock sync probes run four times a second whenever the host announces it, whether or not host frame times are on; frames are scheduled by host time only with host frame times on. `nightjar-cli` writes the same nine columns to its timing CSV.

The last seven columns describe the present scheduler and the decoder queue, and are empty where a frame was not planned: `sched_vsync_ns` (the vsync the frame was planned for), `sched_hold_ms` (the wait before its release), `sched_late` (whether it was behind the game's cadence), `queue_depth` (frames behind it in the decoder), `residency_excess_ms` (its input-to-output time above the ten-second minimum), `in_flight` (frames in front of the compositor) and `drop_reason` (why it was dropped).

**Stream menu → Diagnostics → Measure input latency** runs a software response probe during a stream: on a still host desktop with a visible pointer, it nudges the mouse 15 times and times each nudge until a subsequent frame receives a rendered callback. It reports typical, best and slowest-10% values. Keep the host desktop still between nudges so unrelated updates do not affect the result. This interval ends at the callback; it does not measure physical input-device delay or the screen's actual light output.

**Settings → Advanced → Latency benchmark** runs a 10-second hostless test of frame callbacks, timer wakeups and input dispatch age. Use it to compare devices and settings without a host; **Measure input latency** exercises the stream's software response path. **Share results** on the same screen turns this test and the decoder benchmark into redacted text you can copy or share yourself; see [device results](devices.md).
