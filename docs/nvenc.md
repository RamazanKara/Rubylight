# NVENC

[Rubylight](../README.md) · [Docs](README.md) · [Architecture](architecture.md) · [Hardware matrix](hardware-matrix.md)

Rubylight encodes with AMF on an AMD GPU and with NVENC on an NVIDIA GPU. With `encoder = auto`, the host picks the encoder from the vendor of the GPU that captures. NVENC is called through NVIDIA's driver ABI (`rust/windows/src/nvenc.rs`), API 11 to 13, on the compute conversion's D3D12 device or the capture's D3D11 device. Its settings are the `nvenc_*` keys ([configuration](configuration.md)). Intel and software encoding stay removed; those PCs use [Rubylight 2.6.x](https://github.com/RamazanKara/Rubylight/releases/tag/v2.6.0).

## Parity with AMF

Each row lists a feature the AMF path has and how NVENC provides it. Fake-driver tests in `rust/windows/src/nvenc/tests.rs` cover every NVENC row except the GPU scheduling row, whose tests are in `gpu_priority.rs`.

| Codecs | H.264, HEVC, AV1 | H.264, HEVC, AV1 | The codec check refuses a codec the driver does not list, before the stream starts (Foundation Sunshine). A driver past its session limit (`NV_ENC_ERR_OUT_OF_MEMORY` or `NV_ENC_ERR_INCOMPATIBLE_CLIENT_KEY` on open) is reported as that, naming the apps that usually hold the sessions (out of memory also names exhausted GPU memory), and no other driver API or device is tried. |

## D3D12 conversion

With `gpu_compute_conversion` on (the default), NVENC takes the compute queue's output as AMF does. The session opens on the compute queue's `ID3D12Device` (`Session::open` with an output fence):

- **The GPU waits, not the CPU.** For the D3D12 interface `nvEncMapInputResource` "does not provide synchronization guarantee" (`nvEncodeAPI.h`). Each picture's input is an `NV_ENC_INPUT_RESOURCE_D3D12` whose `inputFencePoint` waits for the conversion's fence at its value.
- **Output goes to READBACK buffers.** Each conversion target gets a buffer of twice an uncompressed picture (at most 16 MiB), registered as `NV_ENC_OUTPUT_BITSTREAM` and passed as an `NV_ENC_OUTPUT_RESOURCE_D3D12`. Its `outputFencePoint` signals the session's own fence.
- **Completion is read from the output fence.** The poll locks a frame once that fence reaches the frame's value and never waits on the CPU. With `nvenc_output_event` (on by default) the fence also wakes the stream thread as the oldest frame is written, instead of on the next 100 µs output poll, which stays as the bound. A frame the fence never reaches fails at the completion timeout.
- **What the D3D12 interface leaves out.** It has no weighted prediction, so `nvenc_weighted_prediction` warns and stays off. Slice delivery returns whole frames there; set `gpu_compute_conversion = false` for either.
- **Driver floor.** The D3D12 interface needs API 12.0, NVIDIA driver 522.25 or newer. An older driver, a missing D3D12 device or a refused session warns (`encoder_conversion`) and converts on the D3D11 graphics queue, as AMF falls back. Native 4:4:4 converts on the D3D11 graphics queue, since the compute conversion writes 4:2:0 only, so encoder focus is off for it.

## Encoder focus

Focus works as on AMF: the D3D12 compute conversion builds the importance map from its still-age detector (`compute::Converter::latest_map`), and the same rules pick the frames that carry it ([`amf::focus`](../rust/windows/src/amf/focus.rs)). No map goes on a keyframe, a recovery picture, the encoder's first frame or the 30 frames after them, or when the map is uniform or not newer than the last one used. Without the D3D12 conversion, focus is off with the same reason as on AMF.

- **Delta map.** NVENC takes the map as a per-picture `qpDeltaMap` (`NV_ENC_QP_MAP_DELTA`): one signed offset per 16x16 macroblock for H.264, per 32x32 CTB for HEVC (the only CTB size NVENC codes) and per 64x64 superblock for AV1 (`nvenc::focus_deltas`). Turning focus on switches `qpMapMode` with a reconfigure, without a reset or a keyframe. The emphasis map is H.264-only, so it is not used.
- **Same weight as AMF.** Each importance step is half a QP (two q-index steps on AV1), the effect AMF's map measured on the RX 7900 XT. The offsets are centred on the picture's mean importance, so the map moves bits between blocks and leaves the frame's QP to the rate control and its one-frame VBV.
- **Startup check.** The probe encodes half-and-half maps, as on AMF, on a session of its own with the delta map and per-block statistics, so the codec check never depends on either. GeForce drivers cap the sessions open at once, so the probe closes the stream's session first and opens it again after, never two at a time. It reads each block's QP from `NV_ENC_OUTPUT_STATS_BLOCK` and needs an effect of 2 QP (8 q-index on AV1). Block statistics need API 12.1, NVIDIA driver 531.61 or newer (`NV_ENC_CAPS_OUTPUT_BLOCK_STATS`); without them focus reports that ROI cannot be verified.
- **Verification during a stream.** `encoder_focus_verify` turns block statistics on when the encoder is made, and `qp_delta` then reports the QP difference between the least and most important blocks, as on AMF.

The D3D11 conversion builds no map, so focus needs the D3D12 conversion on NVENC too.

## Driver settings and Reflex

Beside the encoder, a host that streams with an NVIDIA GPU serves the NVIDIA driver's global 3D settings in the graphics settings panel (Nightjar's stream menu, the console's game page and the native API's [`/radeon` endpoints](native-api.md#radeon-state-and-writes)), read and written through NVAPI (`rust/windows/src/nvidia_settings.rs`): Low Latency Mode, Max frame rate, Vertical sync, Power management mode, Texture filtering quality, Anisotropic filtering and Smooth Motion (driver 571.86 or newer). As with Radeon settings, the host journals the PC's own values before it changes them and puts them back when the session ends, after a crash too; a combination the panel cannot put back exactly reads as `custom` and is left alone. RTSS's limit mode offers NVIDIA Reflex, and a host that streams with an NVIDIA GPU uses it on its own for virtual-display streams and frame-generation games (`framegen::Policy::for_gpu`).

## RTX HDR and RTX Video enhancement

Rubylight's separate, unsigned NVIDIA build (`rust\build.ps1 -Nvidia`, the host's `nvidia-proprietary` feature) runs two of NVIDIA's RTX Video SDK 1.1.0 features on the captured picture before conversion and encoding ([configuration](configuration.md#rtx-hdr-and-rtx-video-enhancement)):

- **RTX HDR** (NGX TrueHDR) turns an SDR capture into an FP16 scRGB picture for an HDR stream. The streamed display stays in SDR while it runs. Its contrast, saturation, middle gray and peak brightness follow the game's NVIDIA driver profile where one sets them.
- **RTX Video enhancement** runs NGX VSR with the output at the input's size, so it removes compression artefacts and sharpens without scaling. Strength 1 to 25, 26 to 50, 51 to 75 and 76 to 100 map to VSR quality levels 1 to 4; 0 turns it off. It takes 8-bit SDR and FP16 HDR captures and leaves a 10-bit PQ capture as it is. VSR's model is SDR, so an FP16 picture goes through an SDR proxy normalized around 203-nit white (`rust/windows/src/shaders/rtx_video.hlsl`), and a resolve pass adds back only the change the model made.

NGX is called from `butterpollo_truehdr.dll` (`rust/truehdr-runtime`), an MSVC adapter the GNU host loads at run time; it is the only code that links NVIDIA's NGX library, built against its static C runtime so that the adapter needs no Visual C++ Redistributable. The host (`rust/host/src/nvidia_enhance.rs`, `rust/windows/src/{truehdr,rtx_video}.rs`) checks both features on the streaming GPU at start, in a process of its own (`butterpollo.exe --nvidia-probe`, given 30 s): a crash or hang inside NGX there turns both off with the reason on the console's app page and leaves a crash report in the profile, and the host starts either way. It reports them in serverinfo's `NvidiaEnhancements` bitmask; the console and Nightjar show their controls only where a bit is set. The enhanced picture is a pool texture of its own, so the encoder is rebuilt when an enhancement starts or stops, and converts on the graphics queue while one runs. A failure turns the enhancement off for the session with a visible warning; it never switches encoders.

The per-app settings, the one pre-encode slot that RTX HDR takes first, and the HDR proxy follow Foundation Sunshine's image enhancement (its per-application design and its DLSS NR HDR filter).

**DLSS denoising is not offered.** Earlier ideas used NVIDIA's DLSS ray-reconstruction denoiser (DLSS NR) as a pre-encode clean-up. NGX gives DLSS features only to applications NVIDIA has registered by application ID, and Rubylight neither presents another application's ID nor patches around that check. DLSS NR proper therefore needs NVIDIA's NGX support for third-party applications; RTX Video enhancement uses the RTX Video SDK, which NVIDIA licenses for redistribution in any application.

## Not run on NVIDIA hardware

The rows above pass the fake-driver tests. No NVIDIA GPU is available to the project, so these behaviours follow NVIDIA's headers and other hosts' code and have not run on one:

- Subframe completion: `hwEncodeStatus` 2 as the end of a picture, and the slice offsets a partial lock reports. The debug lines of the first four frames settle both.
- Keyframes within the one-frame VBV, which the driver does not guarantee.
- Rate control changes applied with frames in flight.
- The stall policy's waits during game loading.
- The D3D12 session: fence points, READBACK output and completion by fence.
- Encoder focus: the delta map's effect per codec, `qpMapMode` switched by a reconfigure, and the block statistics the probe reads.
- The GPU clocks profile: that the driver takes it for the running host, and NVENC's encode time with it on and off on a lightly loaded GPU.
- The driver settings: reading and writing each one through NVAPI, and the restore after a session and after a crash.
- Native 4:4:4: the AYUV and stacked-plane inputs, the High 4:4:4 and FREXT sessions, and the startup check's 4:4:4 encodes. The ignored tests `native_444_keeps_a_one_pixel_chroma_checkerboard` and `native_nvenc_loss_recovery_and_444_hdr_decode` (cases `h264-444`, `hevc-444`, `hevc-444-hdr`) decode the output with FFmpeg and check the chroma at full resolution.
